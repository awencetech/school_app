# Phase 0 MongoDB Instrumentation Verification Report

Generated: 2026-11-11

Scope: staging-only investigation of `/ready` latency and MongoDB performance instrumentation. No code, database data, indexes, authentication behavior, API contract, or production configuration was changed.

## Executive result

`/ready` performs a MongoDB `ping` and takes approximately 199–202 ms in the current staging observations. It reports zero MongoDB operations because the current implementation has two independent instrumentation gaps:

1. The MongoDB client is created without `monitorCommands: true`, so MongoDB command monitoring events are not enabled.
2. Even if command monitoring were enabled, `ping` is not included in the `DB_COMMANDS` allowlist in [backend/performance_instrumentation.js](./backend/performance_instrumentation.js).

The readiness check itself is functioning correctly. It awaits the MongoDB ping and returns HTTP 200 only when the ping succeeds. The zero database metrics are an instrumentation limitation, not evidence that `/ready` avoids MongoDB.

## Exact implementation path

### Readiness handler

[createMongoReadinessHandler](./backend/staging_safety.js:147) does the following:

```js
await client.db(databaseName).command({ ping: 1 });
```

It returns `{ status: 'ready' }` with HTTP 200 after the command succeeds and returns HTTP 503 after a failure. `/health` does not access MongoDB and is intentionally independent of readiness.

### Route registration

The `/ready` route is registered in [backend/server.js](./backend/server.js:7198) with the Mongo readiness handler and the current database name.

### MongoDB client construction

[initializeMongo](./backend/server.js:1842) currently constructs the client as:

```js
client = new MongoClient(mongoUri);
```

It then calls [attachMongoClient](./backend/server.js:1843) before `client.connect()`.

The attachment order is appropriate, but the client options do not explicitly enable command monitoring.

### Command instrumentation

[attachMongoClient](./backend/performance_instrumentation.js:103) listens for `commandStarted`, `commandSucceeded`, and `commandFailed` events. It counts only command names in `DB_COMMANDS`.

The current allowlist includes commands such as `find`, `aggregate`, and `getMore`, but not `ping`. Therefore the readiness ping is ignored even if the client begins emitting command events.

## Root cause

The primary root cause is incomplete MongoDB command-monitoring configuration:

- `monitorCommands` is not enabled in the `MongoClient` options.
- `ping` is omitted from the instrumentation command allowlist.

There is no evidence that `/ready` is excluded from HTTP instrumentation. The response receives a request ID, total timing, database-operation header, database-time header, and `Server-Timing`; only the database fields are zero because the MongoDB event path does not capture the ping.

## Timing and overhead assessment

The current HTTP instrumentation performs minimal in-process work:

- generates one UUID per request;
- wraps `res.write` and `res.end` to count response bytes;
- sets response headers at `res.end`;
- asynchronously appends a record on response finish only when a log path is configured.

No evidence currently shows that instrumentation caused the approximately 200 ms readiness latency. The latency is dominated by the awaited MongoDB readiness operation or its connection/round-trip behavior, but its exact database duration is not measurable until command monitoring is fixed.

One timing limitation should be addressed during the approved correction: the response headers are set in `res.end`, so the MongoDB command completion event must have fired before the readiness handler resolves for the DB time to be included. The MongoDB driver normally emits command completion before resolving the command promise, but this ordering must be covered by a focused test.

The command-context map should also be tested for failed and concurrent commands to ensure entries are removed and request state is not cross-attributed.

## Safe recommended correction — approval required

The minimal staging-safe correction is:

1. Construct the MongoDB client with command monitoring explicitly enabled:

```js
new MongoClient(mongoUri, { monitorCommands: true })
```

2. Add `ping` to the instrumentation command allowlist.
3. Keep the existing two-part staging gate unchanged:

```text
PERFORMANCE_INSTRUMENTATION=true
PERFORMANCE_INSTRUMENTATION_ENV=staging
```

4. Keep query documents and values out of logs.
5. Verify production remains disabled.

This correction changes telemetry only. It does not change readiness behavior, authentication, data, indexes, API contracts, or UI behavior.
